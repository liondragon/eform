## `/eforms/mint`

- Method: `POST` only. Other methods return `405` and `Allow: POST`.
- Body: `application/x-www-form-urlencoded` with `f={form_id}`. JSON bodies are rejected.
- Origin: missing, unknown, or cross-origin requests fail with `403 EFORMS_ERR_ORIGIN_FORBIDDEN`; the endpoint must not emit CORS allow headers.
- Success response: JSON `{ token, instance_id, timestamp, expires }`, where `timestamp` is the token record issue time.
- Error responses are JSON with an `error` code and `Cache-Control: no-store, max-age=0`.
- Rate limits return `429` with `Retry-After`.
- Filesystem mint failures return `500 EFORMS_ERR_MINT_FAILED`.

## Config Contract

- Defaults live in `Config::DEFAULTS`; docs do not duplicate default literals.
- Precedence is code defaults < `eforms_admin_config` < drop-in file < `eforms_config` filter.
- `eforms_admin_config` is a sparse admin override only. It must not store submissions, declined-review records, templates, raw config text, or per-submission state.
- Settings -> eForms may write only the curated allowlist owned by `SettingsFields`.
- Drop-in/filter-controlled values render as externally controlled in wp-admin and are excluded from admin mutation.
- Stored admin secrets are never rendered raw. Blank secret submissions preserve existing stored admin secrets; explicit clear controls remove only the stored admin override.
- Config keys, error codes, `/eforms/mint` JSON fields, and log schemas evolve append-only unless the user explicitly approves a breaking contract change.
- `spam.content_filter.mode` accepts `off`, `suspect`, or `reject`. `spam.content_filter.blocked_terms` is a bounded newline list of plain words or phrases; it is not regex.
- Artifact transport and review representation are one deployment composition, not Config, wp-admin, or form state. Undefined `EFORMS_UPLOAD_COMPOSITION` selects `local_no_processing`; `local_imagick_preview` keeps the same local upload transport and enables only lazy review conversion; `worker_r2_cloudflare` requires an exact HTTPS `EFORMS_WORKER_URL` on an origin distinct from the WordPress home origin, plus the environment ID, active key ID, and unpadded base64url integration key constants. Local preview concurrency defaults to one and accepts only integer values through `LOCAL_PREVIEW_CONCURRENCY_MAX`; invalid optional-preview wiring leaves local artifact upload available but reports the provider unavailable. Invalid Worker wiring fails closed and never falls back locally.

## Managed Upload API

- `POST /eforms/upload-batches` creates or recovers the one batch bound to the validated, unused form token, form ID, instance ID, field key, effective policy fingerprint, storage owner, and exact Worker deployment identity when applicable. Creation and ledger reservation share the ledger lock from the final unused check through batch mutation; a durable marker therefore makes create terminal with `410 EFORMS_ERR_TOKEN`, so a completed token cannot recreate its renamed batch even under concurrent finalization. The browser generates a 32-byte secret with Web Crypto and sends its base64url value in `X-EForms-Batch-Secret`; the server stores only its SHA-256 digest. Retained Worker batches continue only while their persisted Worker origin/environment fingerprint matches the configured deployment; mismatch returns storage unavailable before minting upload, review, inspect, or delete authority.
- Staged create/upload requests return `503 EFORMS_ERR_STORAGE_UNAVAILABLE` before managed-state mutation when the required existing throttle is disabled. Route identities come only from REST URL parameters; JSON, form, or query values cannot override `batch_id` or `upload_id`.
- `GET /eforms/upload-batches/{batch_id}` returns the batch state, effective limits, committed item summaries, and bounded safe summaries of unresolved intents for rerender recovery. On `/eforms/upload-batches/{batch_id}/items/{upload_id}`, a form-encoded `POST` durably authorizes the declared ordinal, display name, bytes, and MIME, then returns either the local transport or a short-lived signed Worker grant. Local composition accepts a multipart `POST` for that intent; Worker composition accepts only a bounded signed-receipt form `POST` after the cookie-free direct upload. `DELETE` is idempotent and tombstones a Worker item before remote release. Rerender recovery restores committed card state without exposing an authoritative-artifact read route to the customer; browser-local selection previews remain presentation-only.
- Every batch endpoint requires `X-EForms-Batch-Secret`. Batch credentials are never accepted from a URL or request body. Create also requires the ordinary validated form-token fields and field key; item authorization and local multipart transfer require the stable browser-generated `upload_id` in the path and the same ordinal in the body. Local pre-transfer authorization reserves the declared artifact plus one exact transient copy; Worker authorization reserves only the final artifact. Integration signing keys never enter Config snapshots, public settings, logs, manifests, or fixtures containing deployment secrets.
- Create, upload, and delete require an explicit same-origin `Origin` header. Credential-authenticated status GETs accept a same-origin or missing `Origin` header because browsers commonly omit it for same-origin reads; cross or malformed origins still return `403 EFORMS_ERR_ORIGIN_FORBIDDEN`, and no endpoint emits CORS allow headers.
- The browser reuses one `upload_id` and ordinal for every retry, and active items have unique ordinals within their batch. Exact create, authorization, local transfer, signed receipt, and delete retries converge on one result; a committed authorization retry returns its safe summary without retransferring bytes. WordPress rejects receipt envelopes above `WORKER_ENVELOPE_MAX_CHARS` before signature parsing. Worker completion revalidates the signed batch, intent, item, ordinal, policy fingerprint, object key/version, bytes, MIME, dimensions, tombstone, and receipt deadline under the normal capacity-before-aggregate lock order. Changed facts or a receipt after removal return generic `409 EFORMS_ERR_TOKEN`; an accepted receipt may settle an already-stored object during its bounded post-intent receipt window without changing first-commit `accepted_at`.
- While the staged path exists, status exposes only `open` or `finalizing`. Upload and delete require `open`. Once finalization begins, all batch mutations fail closed.
- After aggregate rename, after cleanup expiry, when the staged path is absent, or when a route observes the path/manifest removal window of either transition, every batch-ID route returns the same no-store `410 EFORMS_ERR_TOKEN` before credential validation. This result means terminal/unavailable only and never confirms a submission. There is no tombstone, batch index, reverse lookup, directory scan, or submission lookup.
- Malformed or policy-rejected images return `400 EFORMS_ERR_UPLOAD_TYPE`; request or item bodies above a disclosed bound return `413 EFORMS_ERR_UPLOAD_TYPE`; authentication/binding failures and conflicts use `EFORMS_ERR_TOKEN`; capacity or private-storage failures use `EFORMS_ERR_STORAGE_UNAVAILABLE`; rate limits use `429 EFORMS_ERR_THROTTLED` with `Retry-After`. Error bodies contain only `{error}` plus safe field/item context and never contain credentials, paths, signatures, image metadata, or customer values.
- Each create, authorization, local multipart, and receipt-completion request calls the existing origin and per-IP throttle gate exactly once after method dispatch and before Content-Type, credential, payload, reservation, hash, or image validation. Malformed cross-origin requests therefore receive the origin rejection, and same-origin Content-Type failures consume a throttle attempt. A 429 performs no decode or managed-state mutation.
- After a Worker upload grant verifies, the Worker calls its required native rate-limit binding once with the signed intent ID before R2 or Images work. The fixed Anchor-owned limit permits bounded ordinary retries but returns a private CORS `429` with `Retry-After` before provider mutation when exhausted; a missing or failed binding returns `503` and signed health reports storage not ready.
- A Worker upload stream is cancelled no later than the earlier of the signed intent deadline and the Anchor-owned maximum upload duration measured from admission. It cannot extend the remote-uninstall drain window by keeping an R2 write alive after `safe_after`.

### Batch identifier fixture

The batch ID is the unpadded base64url encoding of a full 32-byte HMAC-SHA256 result. Its key is the validated raw form-token byte string. Its message is the concatenation `u32be(byte_length(part)) || part` for this ordered UTF-8 list: `eforms-upload-batch-id`, `1`, form ID, instance ID, lowercase hexadecimal SHA-256 token digest, field key, policy fingerprint. No Unicode normalization, delimiter joining, truncation, random ID, index, or server secret participates.

The canonical fixture uses raw token `token-fixture-01`, form `virtual-quote`, instance `instance-fixture-1`, field `project_photos`, and policy JSON `{"accept":["image"],"max_file_bytes":18874368,"max_files":24,"max_total_bytes":314572800,"upload_mode":"staged"}`. ## Final Form Credential Transport

- Immediately before an ordinary final form POST, `forms.js` emits `eforms_upload_batches[{field_key}][batch_id]` and `eforms_upload_batches[{field_key}][batch_secret]`. `FormProtocol` owns the root, child names, and endpoint header name.
- Submission strips the entire `eforms_upload_batches` root before customer-value normalization, persistence, logging, or email. Validation/challenge rerenders re-emit a field entry only after validating its exact binding, secret, and cleanup deadline and confirming under the ledger lock that the token remains unused. An interrupted pre-ledger `finalizing` claim is reopened while `accept_until` remains live; after that deadline, an exact recoverable claim remains `finalizing` while its credentials are re-emitted so a corrected retry can resume before `delete_after`. A durable ledger marker keeps the claim terminal and its credentials hidden.
- Fresh renders and arbitrary refreshes emit no batch credentials. Credentials never appear in URLs, logs, email, public errors, persisted customer values, or gallery payloads.

## Enhanced Final Submission Response

- The existing final form action remains the only submission URL. A request opts into the response adapter only with the exact `X-EForms-Response: json` header. Missing, malformed, or unsupported values retain the established HTML rerender/redirect behavior.
- The first-party browser sends that header only for a rendered staged-photo form with complete renderer-emitted protocol settings and required browser APIs. Scalar-only forms and unsupported browsers use the HTML fallback. The controller accepts the exact header for any valid eForms POST and does not rediscover template upload capability to reject a scalar form.
- `PublicRequestController` maps the existing `SubmitHandler` result to UTF-8, private no-store JSON. `FormProtocol` owns the header and every introduced response-field name. No new endpoint, submission pipeline, draft store, idempotency key/store, terminal-outcome store, customer artifact route, or browser validation owner exists.
- Accepted and stealth-accepted responses use HTTP `200` and exactly `{ "ok": true, "location": string }`. The location is an existing same-origin `Success` destination. Email failure uses the same safe result-location mechanism without exposing its classification.
- Correctable responses use HTTP `422` and exactly `{ "ok": false, "errors": { "global": [{ "code": string, "message": string }], "fields": { "<field_key>": [{ "code": string, "message": string }] } }, "upload_recovery": { "state": "open" | "finalizing_recovery" } | null, "challenge": null | { "provider": "turnstile", "site_key": string } }`. Field entries are validated template keys in template order and contain stable public codes with resolved safe messages. `challenge` appears only when server correction requires it; `Challenge` owns provider behavior and public metadata, while `FormProtocol` owns only their transport names.
- Other failures retain their existing HTTP status and use exactly `{ "ok": false, "error": { "code": string, "message": string }, "can_retry": true | false, "location": string | null }`. `SubmitHandler` owns the default-false `retry_allowed` fact; `PublicRequestController` copies it to `can_retry`. Neither the controller nor browser may infer retry safety from status, `Retry-After`, or error code. Durable ledger/email boundaries never offer a mail retry.
- Enhanced JSON never includes submitted values, upload summaries or credentials, security tokens, submission IDs, paths, signatures, provider URLs or secrets, or artifact facts. The browser validates a location against its own origin before navigating exactly once; absent, malformed, cross-origin, or unknown locations preserve the current document rather than swapping in HTML, silently reconcile staged uploads through the authenticated status path, and show only retry-safe or terminal next-action copy.
- `FormRenderer` remains the safe HTML fallback owner. On every correctable fallback rerender it may redisplay only descriptor-valid non-file values and exact validated staged credentials. Passwords, files, honeypots, protocol/security fields, malformed values, and every email-failure/terminal response remain undisclosed. The enhanced browser path reuses the existing form, error summary, field invalid state, summary-owned accessible field error mounts, challenge mount, submit-button lock/spinner primitives, and staged uploader; it does not replace the form or reconstruct the uploader after correctable or ambiguous outcomes.

## Managed Review Links

- Rewrite-based pretty permalinks must route registered clean paths through the front controller; Plain and `index.php` PATHINFO structures are unsupported and fail runtime readiness. `GET /review/{token}` renders one gallery; `/review/file/{token}` and `/review/preview/{token}` remain WordPress-owned opaque member URLs while the finalized manifest is available. Unsupported permalink modes fail closed instead of minting a clean URL that the host cannot route. Review paths accept no query parameters, suppress WordPress canonical redirects that would change the opaque path, and do not handle or redirect the superseded `eforms_review`, `eforms_review_upload`, `eforms_review_preview`, or separate `signature` query route. Activation and one-time in-place upgrade handling persist the review rewrite rule; deactivation invalidates persisted rules so WordPress regenerates them without eForms. A logged-in `manage_options` operator may submit the exact gallery URL as a nonce-protected `POST` to update the submission availability or delete the whole finalized submission and its photos through `UploadBatchStore`; no customer-facing or per-photo mutation route exists. A validated Worker-owned member request mints a fresh short-lived exact-object/version/action/recipe grant and redirects to `/v1/review`; the gallery never embeds an expiring Worker grant. Worker preview uses the fixed bounded Images recipe, while download streams the authoritative object as an attachment. Local members stream the authoritative artifact or optional fixed-recipe JPEG directly. Both paths retain private no-store, no-referrer, noindex, and no-sniff headers. A local no-preview card shows **Preview unavailable** and keeps an authorized download control; a failed preview also offers the explicit **Retry preview** action. After preview absence or failure, a local card whose authoritative MIME is browser-native JPEG, PNG, or WebP also offers **Load original**. That action fetches the existing same-origin opaque download URL only on explicit viewer input and presents the response through a page-local object URL; gallery markup never eagerly loads full originals. HEIC, HEIF, and Worker-owned originals remain download-only when no generated preview is available. The gallery assigns at most one preview source at a time and never retries in the background. Each attempt has the `REVIEW_PREVIEW_LOAD_TIMEOUT_MS` deadline; failure or timeout exposes the fallback and releases the next queued preview, so optional local conversion cannot be saturated by one gallery render. A successfully authorized gallery render may opt into the site portfolio lightbox integration with ordinary `ta-gallery__link` / `data-lbwps-*` markup, but invalid, expired, member, deleted, or otherwise unavailable review requests do not enable that integration. Unsupported non-GET methods on matched review paths receive the same unavailable response. Responses never disclose filesystem paths or provider object URLs.
- The WordPress review token is canonical unpadded base64url keyed by `wp_salt('auth')`. Version `4` stores one version byte and the 16-byte submission UUID; file and preview bodies append one byte of upload-ID length plus the exact upload ID. A 16-byte `MANAGED_REVIEW_TAG_BYTES` prefix of HMAC-SHA256 authenticates the length-prefixed domain, version, action, and binary body, making a gallery token exactly 44 characters and binding member tokens to one action. Action-specific Anchor-derived character bounds reject oversized tokens before base64 decoding or HMAC work. Decode, version, length, UUID, upload-ID, and canonical-encoding failures are rejected before manifest lookup; tag comparison is constant-time. WordPress salt rotation intentionally invalidates outstanding links. The token contains the locator, so no token index or reverse lookup exists. Worker review grants use the environment-bound `WorkerProtocol` envelope and expire no later than `WORKER_REVIEW_GRANT_TTL_SECONDS` and, when numeric, the finalized manifest `delete_after`.
- Review availability comes only from the finalized manifest `delete_after`: a Unix timestamp means gallery/member access is available until that time, and `null` means available until manual deletion or uninstall purge. Anonymous expired requests, member requests after expiration, modified, foreign-upload, wrong-version, wrong-recipe, unexpected-query-parameter, and path-like identifiers return the same generic unavailable result. Before GC removes a numeric-expired aggregate, a signed request from a `manage_options` operator may render only management status and whole-submission deletion; it exposes no photos, previews, member links, availability update form, or Worker grants. The Worker verifies its grant before object or cache access and confirms the current exact object version before delivery. Preview absence, saturation, conversion failure, or artifact delivery failure does not mutate submission/finalization state. Possession of a forwarded gallery link grants the same bearer access while the finalized manifest remains available; reloading it mints fresh bounded item grants while the gallery remains valid.
- Lead review details come only from the finalized managed-photo review snapshot. Anonymous signed-bearer gallery HTML may show only the public project summary rows for description and square footage while the gallery is otherwise available; it must not expose name, ZIP, email, phone, listing URL, other submitted values, credentials, paths, provider URLs, or hidden security fields. Logged-in `manage_options` operators may see the full approved lead-review rows. If the snapshot is missing or invalid, the gallery fails closed for public and operator lead details while preserving the existing photo-review behavior allowed by the validated manifest.
- The retained submissions admin list is available only to `manage_options` users and lists currently retained finalized managed-photo submissions from storage-owned traversal. It must not claim all-submissions coverage, listing-only lead coverage, deleted/GC-collected history, stable global newest-first ordering, CRM status, search, filters, export, or a database-backed archive unless a later storage contract adds that surface. Listing-only virtual-estimate submissions remain email-only in this slice.

## Error And Result Contracts

- Public error codes are append-only and owned by the error-code/message owners.
- Token, duplicate, and expired-submission failures share the public message: "This form was already submitted or has expired - please reload the page."
- Email-send failure after ledger reservation redirects to the plugin-owned email-failure result page. The ledger remains burned; runtime must not preserve submitted field values, mint a retry token, render a submitted-content summary, or rerender the form as a retry path.
- A finalized staged submission completes gallery lookup, header validation, and template rendering before persisting `email_attempted_at` immediately before calling `wp_mail()`. Matching recovery may resume only before that marker; after it exists, no retry path invokes mail again. Staged images are represented in email by one signed review link and are never attachments.
- Turnstile Siteverify receives the stable submission UUID as `idempotency_key`, allowing the same pre-email submission recovery to retry provider verification without consuming the single-use response twice.
- Suspicious but delivered emails may add a generic subject tag and `X-EForms-Soft-Reasons` with safe deduplicated soft-reason labels.
- Content-filter suspect decisions are separate from soft-signal threshold math. Delivered suspect emails may add a generic subject tag and safe content-filter metadata such as `X-EForms-Content-Reasons`; public responses and normal logs must not expose raw blocked terms or submitted content.

## Browser Asset Contract

- `forms.js` enqueues only when a form is rendered. Public CSS is split into core form, conditional managed-upload, and signed-review bundles; `assets.css_disable=true` disables every public plugin CSS bundle while leaving wp-admin assets unaffected.
- `forms.js` owns `js_ok`, submit lock, JS token minting, server-error summary focus, and first-invalid focus. Descriptor-marked `tel_us`, `zip_us`, non-negative integer `number`, and `url` controls may use friendly display/entry normalization after `FormRenderer` emits the descriptor-owned protocol attributes; browser submit sends canonical values, and server validation/coercion remains authoritative.
- `forms.js` also owns every staged uploader queue. Item states are `queued`, optional `preparing`, `uploading`, `verifying`, `uploaded`, `failed`, `removing`, and `removed`; transfer progress reaching 100% enters `verifying` with **Finishing upload...** until WordPress confirms manifest commit. The accepted extension determines the canonical declared image MIME when browsers omit `File.type`, while server inspection remains authoritative. Local composition uses same-origin multipart; Worker composition requires a distinct HTTPS origin and uses a cookie-free `XMLHttpRequest` `PUT` with only the returned grant and MIME, then posts the signed receipt to WordPress without creating a second queue or provider-specific card state. Final-submit recovery never exposes upload-status or reconciliation controls to visitors; the existing Send button is the only retry control when retry is safe.
- `media.client_preparation` is a deployment-only `off|opportunistic_jpeg` mode and defaults to `off`. In opportunistic mode, one shared browser Worker slot may inspect and re-encode an eligible JPEG with the Anchor-owned fixed recipe before authorization; uploads retain their separate three slots, non-JPEG formats bypass preparation, and no full-pixel main-thread fallback exists. The runtime authorizes and uploads exactly one chosen artifact, aborts preparation on removal, and falls back silently to the unchanged source only when it still fits the effective server limits; it never uploads both versions or emits preparation claims in browser credentials.
- Any selected item in `queued`, `preparing`, `uploading`, `verifying`, `failed`, or `removing` blocks final submission. Validation-rerender restoration is also a blocking phase: picker mutation and submission remain disabled until one complete authenticated status snapshot has been validated and applied. Network failures, `408`, `429`, `5xx`, and malformed status responses retain the batch credentials and expose a restore retry; only a definitive terminal response or expiry makes the runtime unavailable. A committed item confirmed by batch status remains `uploaded` and submittable even when its browser-local selection preview cannot be restored or decoded. A safe unresolved intent restores as a failed, non-retryable card that the visitor can remove and select again. The runtime reconciles ambiguous upload and delete outcomes through authenticated status, serializes item cleanup within each batch, preserves and restores the actual per-form submit label, freezes mutations when final submission begins, clears/disables staged file inputs, and writes only the protocol-owned hidden credentials. Destroying or removing a form aborts its active runtime-scoped batch create/restore request plus item transfer and control requests, discards any late response, and never starts an item body afterward.
- A server-rendered staged picker is disabled and unnamed with a `<noscript>` explanation. JavaScript enables it only as picker transport; there is no synchronous multipart fallback. A created open batch retains its credential transport even after every item is removed, so a validation rerender can restore the same batch; arbitrary refresh does not restore a batch.
- Managed browser fields require the complete renderer-emitted `FormProtocol` upload settings. Each managed mount carries the exact capped picker ID emitted by the renderer; browser association never reconstructs or infers that ID from a form or field suffix. Missing or partial protocol settings leave the staged picker disabled; browser code has no local fallback copy of shared header, field, parameter, or data-attribute names.
- Ordinary JS-minted forms may reuse a valid token from `sessionStorage`. A staged JS form on a fresh render has no recoverable batch secret, so it removes any cached token and mints a new token before enabling uploads. A validation rerender carrying complete server-validated batch credentials keeps its rendered token and restores that exact batch instead.
- Managed fields expose empty, preparing, uploading, verifying, uploaded, failed, removing, blocked, and expired states with live-region announcements and progressbar semantics. Create and status responses carry the effective server limits; the renderer emits the same effective limits, and the browser applies the response before transferring an item body. An initial create with expired form credentials returns terminal `410 EFORMS_ERR_TOKEN`; after a terminal batch response, the field rerenders every card without mutation controls, blocks their handlers plus upload/submission, and instructs the visitor to reload. Local `accept_until` expiry rerenders every card, hides retry controls, and blocks upload/submission; open-batch status and cleanup remain available only until `delete_after`.
- Plugin CSS owns managed-field structure. Themes may set only `--eforms-upload-accent`, `--eforms-upload-track`, `--eforms-upload-border`, `--eforms-upload-card-bg`, and `--eforms-upload-error`.
- JS-minted forms must block submission until token minting succeeds.
- JS must not overwrite non-empty `eforms_token`, `instance_id`, or `timestamp` fields.
- Mixed-mode pages call `/eforms/mint` only for JS-minted forms and never for hidden-token forms.
- The Turnstile provider script is enqueued only when a challenge is rendered. Only the site key may reach browser markup; secret keys stay server-side.
