# Runtime Storage

This file captures runtime storage, token, upload, and maintenance contracts. Operator setup guidance belongs in `README.md` and `docs/overview.md`; exact implementation lives in code and tests.

## Private Storage Root

All runtime artifacts written under `wp_upload_dir()` live under:

```text
${uploads.dir}/eforms-private/
```

Fail2ban emission is the exception: `logging.fail2ban.file` may point at an absolute operator-managed log path, or at a safe relative path resolved under `${uploads.dir}`. Relative Fail2ban paths must not contain `..` segments.

Runtime must create `index.html`, `.htaccess`, and `web.config` deny/protection files for private directories it owns. Directory permissions are `0700`; file permissions are `0600`. Permission or hardening failures fail closed on paths that need private storage.

## Layout

| Artifact | Path |
| --- | --- |
| Token records | `tokens/{h2}/{sha256(token)}.json` |
| Ledger guard, markers, and shard locks | `ledger.lock`, `ledger/{form_id}/{h2}/{submission_id}.used`, and `ledger/{form_id}/{h2}/.lock` |
| Uploads | Ordinary: `uploads/{Ymd}/{submission_id}-{field_ordinal}-{item_ordinal}-{sha16}.{ext}`; staged recovery: `uploads/{h2}/{submission_id}/{submission_id}-{field_ordinal}-{item_ordinal}-{sha16}.{ext}` |
| Open/finalizing managed batches | `staged/{h2}/{batch_id}/` |
| Finalized managed submissions | `submissions/{h2}/{submission_id}/manifest.json` plus `review.json` for managed-photo submissions |
| Local authoritative artifacts | `artifacts/{h2}/{object_identity}/{object_version}.artifact` |
| Optional local review previews | `preview-cache/{h2}/{sha256(object_key, object_version, recipe)}/preview.jpg` plus producer/fence files and global slot locks |
| Managed capacity state | `managed-capacity.json` and `managed-capacity.lock` |
| Upload lifecycle state | `upload-lifecycle.lock`, `managed-purged`, and a temporary `remote-purge.json` drain record during Worker/R2 uninstall |
| Throttle state | `throttle/{h2}/{ip_hash}.tally` and `.cooldown` |
| JSONL logs | `logs/` |
| Fail2ban file | Safe relative `logging.fail2ban.file` under `${uploads.dir}` or an absolute operator-managed path; plugin rotations use numeric `.N` siblings |
| Declined-review files | `declined/` |
| GC lock/progress | `gc.lock` |

`{h2}` is the first two hex characters of `sha256(id)` and is derived through the shared helper.

## Filesystem Assumptions

- Token writes use write-to-temp plus rename in the same directory.
- Ledger reservation uses atomic exclusive-create while holding the stable shared `ledger.lock` guard and its shard lock. Any mutation permitted only for an unused token holds both locks from the final marker check through the mutation.
- Throttling and JSONL logging require reliable `flock()` semantics.
- Each runtime-health directory check names its temporary probe with `RUNTIME_HEALTH_PROBE_ENTROPY_BYTES` and removes only that invocation-owned path, so a stale or overlapping probe cannot redirect cleanup or make another diagnostic fail.
- Multi-webhead/container deployments must share persistent storage that preserves those filesystem semantics. Ephemeral per-container storage is unsupported.

## Token And Ledger Contract

- Hidden-mode GET render mints and persists a hidden token record before emitting hidden security fields.
- JS-minted mode obtains token records only through `POST /eforms/mint`.
- Token records include `mode`, `form_id`, `instance_id`, `issued_at`, and `expires`.
- Posted mode hints are informational; validated mode comes from the persisted token record.
- Token-record validation is read-only and does not mutate records, headers, or ledger state. Managed batch creation separately enters the ledger-owned unused-token guard before touching aggregate state.
- The ledger marker is reserved immediately before side effects. Batch creation and marker reservation share ledger serialization, so creation either completes before reservation or observes the consumed token and performs no managed-state mutation. `EEXIST` is duplicate submission; other filesystem failures map to ledger IO failure.
- Once a ledger marker exists, only `wp eforms gc` may delete it.
- Email-send failure after ledger reservation does not reopen the token.
- Managed finalization freezes an `open` aggregate as `finalizing(submission_id)` before ledger reservation only when the lock-held resolved item set exactly matches the snapshot already used for submission validation. A concurrent upload or deletion rejects the stale claim while leaving the batch open for a clean retry. Before `accept_until`, validation or challenge failure reopens an unused recovered claim. After `accept_until`, exact recovery keeps that claim `finalizing` and may re-emit its credentials for a corrected retry through `delete_after`. The matching submission may recover an established claim only before `email_attempted_at`; a foreign claim or any replay after the marker remains a duplicate failure.

## Cache Safety

Responses that embed hidden security metadata, respond to `eforms_*` result query args, or return PRG result pages must send private no-store cache headers. If headers cannot be set for a hidden-token response, runtime must not mint or emit hidden tokens in a cache-unsafe response.

## Upload Policy

- Synchronous upload token mappings:
  - `image` -> `image/jpeg`, `image/png`, `image/gif`, `image/webp`
  - `pdf` -> `application/pdf`
- Default exclusions include SVG and TIFF. Synchronous uploads exclude HEIC and HEIF. A staged field accepts only `image`, which maps to JPEG, PNG, WebP, HEIC, and HEIF while rejecting GIF.
- Synchronous and local staged validation require agreement between accept token, extension, and `finfo` MIME result. Worker-staged validation enforces the same declared-name/MIME contract at authorization and performs authoritative byte inspection at the Worker/Cloudflare boundary.
- `fileinfo` is required for synchronous and local staged upload attempts; those attempts fail deterministically when it is unavailable. A Worker-only staged composition does not route artifact bytes through PHP inspection.
- Display filename starts from the client name but strips paths, control characters, CR/LF, unsafe dot/space runs, and excessive length.
- An ordinary synchronous stored filename remains private and collision-resistant at `{Ymd}/{submission_id}-{field_ordinal}-{item_ordinal}-{sha16}.{ext}`. A synchronous file accompanying a staged submission uses `{h2}/{submission_id}/{submission_id}-{field_ordinal}-{item_ordinal}-{sha16}.{ext}` so recovery ordinals and lookup are stable and bounded to that exact submission directory. Recovery ordinals come from the upload descriptor position and original request item position, so omitting an earlier optional field or item does not change a later file's identity. Validation and writes for every staged synchronous commit or recovery run through one exact-reuse-or-collision path under the finalized aggregate's per-submission lock.
- Runtime must not overwrite existing upload paths.
- Synchronous uploads are deleted after successful send unless retention applies. Non-staged failures and transport failures after a durable staged email-attempt marker follow synchronous retention policy. A staged local-preparation failure before that marker preserves the exact stored paths for the permitted recovery; a successful corrected commit removes preserved owner files omitted by the retry. When ordinary retention is zero, GC still reclaims abandoned staged-recovery files after `MANAGED_FINALIZED_TTL_SECONDS`.

### Managed staged images

- A staged field accepts JPEG, PNG, WebP, HEIC, and HEIF through the sole `image` token and rejects GIF. Accept token, extension, and detected MIME must agree; exact bytes, display-oriented dimensions, and the `MANAGED_ARTIFACT_MAX_*` bounds are verified without requiring normalization or a generated preview. JPEG dimensions account for EXIF orientation before persistence. PNG and WebP animation inspection is bounded by `MANAGED_IMAGE_CONTAINER_MAX_CHUNKS`. HEIC/HEIF acceptance requires an unprotected supported primary still-image item definition and decoder-free ISO-BMFF inspection of coded and displayed dimensions bounded by `MANAGED_HEIF_MAX_BOXES`, `MANAGED_HEIF_MAX_ASSOCIATION_ENTRIES`, and `MANAGED_HEIF_MAX_ASSOCIATIONS`; protected items, sequence brands, and track/fragment containers are rejected. A direct primary item must have nonempty media-backed extents; a tiled `grid` primary must have a bounded matching descriptor, exact derived-image references, and media-backed HEVC tile extents. Local no-processing acceptance does not require Imagick.
- Optional browser JPEG preparation completes before intent authorization and therefore before declared-byte reservation. One Anchor-owned preparation slot is independent of the three upload slots; only the chosen source or prepared JPEG contributes to per-file and aggregate browser policy checks, intent facts, transfer bytes, and server inspection. Preparation mode, recipe, source facts, and fallback reasons never enter managed manifests; server-side validation remains authoritative.
- The accepted upload artifact is authoritative for the submission retention period. Local storage or the deployment-bound Worker writes it once under the same opaque object-key contract and returns an immutable version; optional previews are presentation caches and never determine upload success, manifest state, finalization, or capacity ownership. For Worker-owned artifacts, one private zero-byte validation record binds the exact R2 version/etag to the inspected media facts. A version-bound zero-byte validation lease record admits one inspector at a time. Active acquisition, stale takeover, and release are exact-etag conditional state transitions, so an old owner cannot overwrite its successor; abandoned work becomes reclaimable only after the bounded upload window. Concurrent or response-loss retries can return a receipt only after the validation record exists. A request-local validation failure preserves the write-once object and releases its lease; the WordPress-owned intent/tombstone and exact GC deletion path remain responsible for physical cleanup, with the whole-namespace lifecycle rule as the crash fallback. Exact object deletion removes the artifact and both version-bound records as one idempotent operation.
- `LocalPreviewProvider` creates at most one fixed-recipe JPEG for an immutable local object/version. It checks the cache under a nonblocking per-object producer lock, takes one nonblocking global slot bounded by `LOCAL_PREVIEW_CONCURRENCY_MAX`, and asks the capacity facade to preallocate the bounded output while accounting for outstanding local artifact and transient claims. The physical preallocation preserves `MANAGED_UPLOAD_MIN_FREE_BYTES` for already-authorized and later uploads without making replaceable cache bytes authoritative capacity state; conversion remains outside the capacity lock and atomically publishes the result. Saturation is transient; conversion or cache failure keeps the authoritative download available. Local artifact deletion fences and removes the matching cache before deleting bytes so a late preview cannot recreate it. Normal bounded GC preserves that fence through `MANAGED_ORPHAN_CLEANUP_GRACE_SECONDS`, then removes the fence, producer lock, identity directory, and empty shard; dry-run reports the same candidate without mutation. Worker preview caching remains internal and unreachable without a valid review grant plus a currently matching R2 object version.
- Managed manifest version `5` is the sole accepted schema; no older reader, alias, or dual writer exists. Each aggregate persists one immutable `artifact_store` (`local` or `worker`) and `artifact_store_identity` at creation. Local identity is the fixed `local` owner; Worker identity is a SHA-256 fingerprint of the stable Worker origin and environment, excluding rotating signing keys. Authorization, completion, review, GC, reconciliation, and uninstall route from those persisted values rather than the deployment's current composition; a Worker deployment mismatch fails closed before issuing a remote request. An open manifest has disjoint `intents`, `items`, and `tombstones` maps plus `artifact_bytes`. An intent stores exactly `intent_id`, `upload_id`, `ordinal`, `display_name`, `declared_bytes`, `declared_mime`, `object_key`, `policy_fingerprint`, `created_at`, `expires_at`, and `reserved_bytes`. A committed item stores exactly `upload_id`, `ordinal`, `display_name`, `bytes`, `mime`, `width`, `height`, `object_key`, `object_version`, and `accepted_at`. A tombstone retains `bytes`, `object_key`, the known `object_version` or an empty version, `deleted_at`, and capacity-release phase flags.
- Authorization persists the bounded intent and exact declared-byte reservation before returning either transport. Every reservation persists its `artifact_store`; local pre-transfer authorization also persists one declared-byte transient allocation claim, while Worker authorization claims zero transient bytes. Local completion uses bounded inspection facts; Worker completion first verifies an environment-bound signed receipt, then revalidates the exact intent, policy, immutable object facts, tombstone state, and reservation while holding capacity before aggregate locks. A valid receipt may complete after intent expiry only through its bounded receipt deadline. First completion assigns `accepted_at` from the WordPress commit clock and atomically replaces the intent; exact retries settle retained accounting without changing identity or `accepted_at`, while changed facts fail generically.
- Browser and email values contain bounded public facts only. They never contain stored paths, provider URLs, grants, signing material, or capacity-record identities.

## Managed Aggregate Contract

- Each staged aggregate uses a stable sibling `.{batch_id}.lock`; each finalized aggregate contains a stable `.lock` alongside `manifest.json`. Existing staged aggregates may still have the former adjacent `<batch_id>.lock` only as legacy synchronization state used to create the sibling lock. Manifest and capacity-record writes use write-to-temp plus same-directory rename while their owning lock is held. Authoritative artifact bytes live outside aggregate directories and remain addressed by manifest object identity. Controllers, submission, email, review templates, and GC never write these files directly.
- `UploadBatchStore` derives `batch_id` from the exact public-contract fixture algorithm. One exact form/token/field/policy binding therefore has one locatable active path without an index or scan. The manifest stores only the batch-secret SHA-256 digest and the exact binding needed for verification.
- Aggregate state is `open -> finalizing(submission_id) -> finalized`. Authorization, completion, and item deletion are valid only in `open`; finalization requires the exact committed-item snapshot and zero intents. Delete records a tombstone and removes the intent or item before physical deletion, so late completion cannot resurrect the logical ID. Exact reauthorization of an expired local intent first runs that same tombstone, object-fence, and capacity-release protocol before returning a generic conflict; the expired ID stays terminal while a fresh ID can proceed without leaving an invisible finalization blocker. The lifetime bound counts intents, items, and tombstones; once full, further distinct IDs are rejected. Finalizing and finalized aggregates are immutable through batch endpoints.
- Finalization writes the durable finalizing claim, holds the staged sibling lock at `staged/{h2}/.{batch_id}.lock` across the atomic same-filesystem directory rename to `submissions/{h2}/{submission_id}/`, then releases it and acquires the destination's internal `.lock` before completing the finalized manifest. Existing staged aggregates with the former adjacent `staged/{h2}/{batch_id}.lock` create the sibling lock while holding that legacy lock, then release it before a rename. Rename does not change managed-capacity usage. If execution stops during that lock handoff, exact same-submission pre-email recovery acquires the destination lock and completes its `finalizing` manifest. After rename, no batch route looks up the submission aggregate.
- `UploadBatchStore` strictly validates the complete manifest schema, nested types, disjoint intent/item/tombstone identities, object identity, accounting totals, policy fingerprint, state-specific fields, and aggregate identity before any caller consumes it. A staged manifest's `batch_id` must match its batch directory, and a submission manifest's claimed submission ID must match its submission directory. Structurally or semantically malformed or misplaced JSON fails closed as storage corruption.
- Finalized managed-photo submissions include `review.json`, an operator review snapshot sidecar built from post-coercion submission values by `SubmissionReviewSnapshot`. It is written under the finalized aggregate lock before external email delivery and is deleted with the aggregate by operator deletion, GC, or uninstall purge. The manifest remains the authority for photos, artifacts, capacity, storage-owner identity, and availability; customer fields must not be stored in `manifest.json`.
- `review.json` version `1` stores only `schema_version`, `form_id`, `template_version`, `submission_id`, `submitted_at`, `title`, `header`, and `operator_rows`. The virtual-estimate snapshot may include display rows for name, ZIP, email, phone, project description, square footage, and optional listing URL. It must not contain credentials, paths, signatures, provider URLs, raw upload metadata, hidden security fields, arbitrary unmapped submitted values, CRM delivery metadata, or admin-list ordering/index state. Missing, malformed, or semantically invalid sidecars fail closed for lead details and never authorize reading raw submitted values from another source.
- Listing-only submissions do not create managed upload aggregates and do not require a `review.json` sidecar. A retained-submissions list can enumerate only currently retained finalized managed-photo aggregate directories unless a later contract adds a separate submission index or archive. That enumeration is owned by `UploadBatchStore`, uses the existing bounded deterministic shard traversal over retained aggregate directories, validates each finalized manifest and `review.json` sidecar under the aggregate lock, and returns only compact admin facts for rows and signed-view URL inputs. Missing, malformed, corrupt, deleted, GC-removed, listing-only, or path-only entries are absent or fail closed; list rows never expose paths, object keys, provider identities, credentials, arbitrary submitted values, or admin-list index state.
- `accept_until` is the validated token record expiry. An abandoned open batch starts with `delete_after = accept_until + MANAGED_STAGED_DELETE_GRACE_SECONDS`; upload and submission end at `accept_until`, while open status/delete may continue only until `delete_after`.
- Successful finalization replaces the staged cleanup deadline with finalized `delete_after = finalized_at + MANAGED_FINALIZED_TTL_SECONDS`. For finalized aggregates, `delete_after` is the single availability authority: a Unix timestamp permits review access until that time and makes the aggregate GC-eligible afterward, while `null` means available until nonce-protected `manage_options` operator deletion or explicit uninstall purge. Numeric-expired aggregates may still be manually deleted before GC removes them, but they do not expose photos, member links, previews, or availability updates.
- The global object total includes local and Worker committed artifacts, active declared-byte reservations, and delete-pending objects until confirmed absent. Managed capacity accounting requires 64-bit PHP integers. Every combined mutation takes `managed-capacity.lock` before the aggregate lock; artifact transfer and image inspection run outside both. Authorization reserves declared bytes only when the result stays within `MANAGED_OBJECT_MAX_BYTES`; local free-space projection includes only local final-byte reservations plus every local durable transient claim and retains `MANAGED_UPLOAD_MIN_FREE_BYTES`. Worker reservations remain in the global object budget but never consume the WordPress filesystem projection. Completion settles the exact reservation after manifest commit, and exact committed retry repairs conservative overcount. Every positive-byte reservation retains its object and storage-owner identity; a stale Worker reservation whose manifest write never became durable remains charged through the intent, upload, and clock-skew drain, then is fenced against reuse and deleted through that persisted owner identity before accounting is released. Deletion first persists its tombstone and capacity-release intent; local deletion then serializes absence under the object lock, while Worker deletion remains charged and marked pending until the remote lifecycle owner confirms exact-version absence. Reconciliation treats an unreleased tombstone as materialized and cannot release it merely because no local file exists. Crashes may overcount but never undercount an object that may exist; unsafe observation fails closed.
- Worker/R2 capacity health and explicit reconciliation compare the validated capacity record with every active manifest authority rather than local disk bytes. Capacity health carries every retained storage-owner identity; deployment readiness fails before its provider probe if any retained Worker fingerprint differs from the configured origin/environment. Reconciliation settles retained committed reservations, preserves active remote authority, and removes at most one stale pre-manifest Worker orphan per run through the deployment-bound remote deletion owner; without that owner, required remote cleanup fails closed. Signed Worker health separately proves the R2, Images, and upload-rate-limit bindings are present.
- `WorkerClient` supplies one structured event per signed delete, inspect, or health operation with only a closed operation name, outcome class, latency bucket, retry disposition, and caller-owned lifecycle phase; the logging owner may add its normal request/runtime envelope. Worker-supplied metadata never includes filenames, customer values, object keys or versions, grants, receipts, provider responses, or secrets. GC separately owns aggregate scan and capacity-budget totals in its existing summary event. The minimal and JSONL sinks retain those bounded operational fields.
- Remote GC converts expired intents to durable tombstones, releases capacity and aggregate locks before exact-version Worker deletion, then reacquires and revalidates the manifest before releasing accounting. Aggregate expiry writes an idempotent capacity-release receipt before deleting the manifest, so a retry cannot double-release after either write window. The first provider failure stops further remote calls in that run and retains the locator, manifest, tombstone, and byte charge. A read-only exact-version Worker inspection supports control-plane restore sign-off; it does not create review delivery or mutate submission state.
- Finalized manifests persist `email_attempted_at` after local message preparation succeeds and immediately before transport invocation. This creates an accepted loss window if the process stops before `wp_mail()`; it prevents duplicate mail and is never cleared. Before this marker, the finalized aggregate lock serializes initial and recovered synchronous-file commits, and local preparation failures preserve the exact files. If a concurrent recovery loses the marker gate, it must not delete paths shared with the winning transport attempt; normal post-transport retention remains the winner's responsibility.

## Throttle Contract

- Throttle is optional and per resolved client IP.
- It uses a fixed 60-second byte-counter window plus optional cooldown sentinel.
- On lock acquisition failure, throttle enforcement is skipped for that request and a warning is logged when logging is enabled.
- Hard-fail response semantics:
  - hidden GET render: HTTP 200 inline per-form error with no-store cache headers
  - POST submit: HTTP 429 with `Retry-After`
  - `/eforms/mint`: HTTP 429 with `Retry-After`
  - staged create/upload: HTTP 429 with `Retry-After`, before decode or managed-state mutation
- Staged create/upload fail closed while the throttle is disabled. They reuse this throttle's existing window, cooldown, lock-failure behavior, and operator settings; no second limiter or configuration surface exists.
- Runtime readiness requires the configured per-IP window to cover one batch request plus two WordPress requests for every item allowed by the largest active staged field. Lower retained settings fail the doctor check rather than being silently raised; operators should add further headroom for retries and customers sharing one public IP.

## GC Contract

- The plugin does not schedule WP-Cron for GC.
- Operators run `wp eforms gc` through system cron or an equivalent external trigger.
- GC uses a single-run lock to avoid overlapping work.
- Applying GC persists the next-family position and bounded cursors for every budgeted artifact family in `gc.lock` so repeated small runs advance regardless of scheduler cadence instead of rescanning an early fresh prefix. Managed aggregates resume within their shards; recursive file families resume after the last visited relative path; declined-review cleanup resumes after the last visited entry. Directory discovery streams lexicographically bounded in-memory pages instead of materializing whole directories; filesystem enumeration cost still follows the number of entries in the directory being visited. Dry-run reads but does not advance progress; losing progress only restarts discovery from the beginning.
- GC targets expired token records, eligible ledger markers and orphan ledger shard locks, stale throttle files, retained synchronous uploads plus abandoned staged-recovery files, expired managed aggregates, safely aged local preview-deletion fences, old logs, Fail2ban rotated siblings, and old declined-review files.
- Managed cleanup reads manifest `delete_after` and immutable `artifact_store`, deletes every manifest-owned authoritative artifact through that store, releases its accounting, and then removes the aggregate. Explicit operator deletion uses the same artifact-store and accounting owner for one finalized aggregate without waiting for `delete_after`. Changing the active deployment composition never reclassifies retained aggregates. Discovery and deletion never follow symlinked shards, aggregates, locks, manifests, artifact directories, or unrecognized partial residue. A manifest-less staged directory is collected only when its identifier, shard, entries, and observed age match the creation protocol and exceed `TOKEN_TTL_MAX + MANAGED_STAGED_DELETE_GRACE_SECONDS`; exact owner-created initial-manifest temp files remain recognizable and recoverable, while corrupt manifests and unrecognized residue fail closed. Dry-run and apply summaries report staged and finalized aggregates separately; pre-expiry finalized aggregates are never deleted by GC.
- Ledger markers are eligible only after `TOKEN_TTL_MAX + LEDGER_GC_GRACE_SECONDS` from marker mtime. A ledger shard `.lock` is eligible on the same age gate only when its shard has no `.used` marker and GC can take the stable `ledger.lock` guard exclusively and then the shard lock without waiting. The root guard is never garbage-collected.
- Dry-run reports candidate counts and bytes without deleting.

## Uninstall Purge Contract

- The existing `install.uninstall.purge_uploads` decision owns all private upload lifecycle data; staged uploads do not add a second purge flag.
- When upload purge is disabled, staged/finalized aggregates, authoritative artifacts, optional local preview caches, and managed-capacity state remain untouched.
- Every token, ledger, throttle, synchronous-upload, managed-upload, preview-cache, and upload-GC mutation holds a shared `upload-lifecycle.lock` lease before taking its owner-specific locks. When upload purge is enabled, uninstall takes that lifecycle lock exclusively without waiting, then acquires `managed-capacity.lock`, pre-acquires every staged/finalized aggregate lock, and writes the `managed-purged` barrier. With both global locks still held, it releases aggregate handles before deleting the staged, submission, artifact, and preview-cache roots so Windows can remove lock files. A successful purge removes `managed-capacity.json` only after all managed roots are absent, then retains the lifecycle lock, capacity lock, stable ledger guard, and barrier so queued writers fail closed; activation removes only the barrier under the exclusive lifecycle lock.
- Worker/R2 uninstall uses the same purge decision and barrier. Detection validates manifests and the capacity ledger, so a reservation-only Worker locator still requires the remote drain when its aggregate was lost. Its first attempt persists `remote-purge.json` without object keys or secrets and returns failure plus `safe_after`; it never waits for the grant window in one request. The drain fingerprint binds the stable Worker origin and environment identity but excludes rotating signing-key IDs, so normal key rotation does not invalidate an in-progress purge. Activation removes the barrier but may leave the interrupted drain record as evidence; if uninstall is requested again after reactivation, it establishes a new barrier and replaces the stale timing with a full fresh drain window before any remote delete. A retry before the current `safe_after` performs no remote call. Each ready retry processes at most one code-owned aggregate or orphan-reservation page and checkpoints its phase/cursor. Aggregate pages perform idempotent exact-version deletes outside capacity and aggregate locks, then durably checkpoint the idempotent capacity release before removing each manifest; the final reservation phase likewise deletes every capacity-owned Worker locator whose aggregate authority was lost before releasing its exact reservation. It removes the drain record only after remote and local purge finish. Provider, lock, corrupt-state, or deletion failure preserves the barrier, record, remaining manifests, and accounting for another supported WordPress deletion attempt; reactivation after a partial page therefore reads a consistent capacity total.
- The R2 `artifacts/` lifecycle rule is a late whole-namespace backstop for authoritative objects and their zero-byte validation records, not application truth. `worker/scripts/verify-r2-lifecycle.php` computes its minimum whole-day age from Anchors and reads the real rule with operator-held management credentials that never enter WordPress or the Worker.
- A lock-acquisition or deletion failure leaves recoverable residue and never broadens cleanup outside `${uploads.dir}/eforms-private/`. If validation rejects an already-materialized authoritative artifact, failure of its tombstone/deletion protocol is returned as the terminal storage error rather than being hidden by the validation result.
